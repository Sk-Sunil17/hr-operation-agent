===============================================================================
 PART A — WHAT IT IS
===============================================================================

A1. ONE PARAGRAPH
-----------------

An HR operations agent that handles the routine back-office work of a people
team — answering policy questions, processing forms, updating records,
scheduling interviews, checking new starters are ready — and which is built so
that it CANNOT send an answer it cannot prove, and CANNOT change a real system
without a named person approving it first. Every company that uses it
configures it with its own files, and can only ever make it stricter.


A2. THE TWO SENTENCES THAT DEFINE IT
------------------------------------

  1. It cannot send a claim it cannot cite to a policy version in force today.
  2. Everything a company differs on is configuration, not code.

Everything else in this document is a consequence of those two.


A3. WHY THAT MATTERS (the commercial argument)
----------------------------------------------

Every HR AI tool on the market is built to ANSWER. The whole design is "reduce
tickets". In HR that is the wrong objective, because a confident wrong answer
is not a bad user experience — it is a legal event. Tell someone they are
entitled to leave they are not entitled to, and the company is bound by it.

So this is built the other way round: it starts from what it is NOT allowed to
do, and the ability to answer is what is left over. That is why it has four
possible outcomes instead of one.


A4. THE FOUR OUTCOMES
---------------------

  auto       answer it now, on its own
  prepare    draft it, show a preview, wait for a person to approve
  hand_over  a person takes it; the requester is told, warmly and immediately
  refuse     decline it, say why, and offer the next step

A rule decides which. Not the AI. The rule reads facts that came from systems,
never from the wording of the message.


A5. THE FIVE FEATURE AREAS
--------------------------

These are the five things to be able to demonstrate. All five were verified
working end to end on all three companies.

  1. EMPLOYEE ENQUIRIES
     Policy and entitlement questions. Routine ones are answered directly by
     quoting the policy verbatim with version and section. Personal ones wait
     for a person. Sensitive ones are never answered at all.

  2. DOCUMENT PROCESSING
     Forms arriving. Read against the company's own form templates, every field
     read back for a person to confirm. Incomplete forms name exactly what is
     missing. Sensitive document types are never read. Unrecognised documents
     are not guessed at.

  3. POLICY LOOKUP
     A versioned, effective-dated policy library. Only the version in force
     today can be quoted. Retired and draft versions are excluded. If two
     versions claim the same day, it refuses to answer rather than pick one.

  4. INTERVIEW SCHEDULING
     Reads the panel's free/busy, applies the company's notice period, buffer
     and daily limits, proposes times, and prepares the calendar hold, the
     candidate's email (with a real .ics attached) and the panel's brief. One
     approval commits all three. Also handles rescheduling and cancellation.

  5. HR ADMINISTRATION
     Changes to records the company holds — address, phone, emergency contact.
     Prepared with a before/after preview, committed only on approval. Plus
     onboarding readiness checks and offboarding checklists.

  A hard line that cuts across all five: no tool in this system can write pay
  or grant access. That is checked when a company's config loads AND again at
  runtime, because a guarantee worth having is worth checking twice.


===============================================================================
 PART B — HOW IT WORKS
===============================================================================

B1. THE LOOP
------------

Every request, from any channel, goes through the same eight stages in the same
order. The dashboard draws them as seven numbered circles across the top.

   receive -> understand -> retrieve -> decide -> draft -> verify -> act -> audit

Three things about that order are deliberate, and they are the whole design:

  * The raw message is STORED BEFORE anything looks at it. A crash loses
    nothing; a message delivered twice is recognised and not acted on twice.

  * The policy search happens BEFORE the decision, because "is there a policy
    in force covering this" is a fact the rules need to test. That search is
    read-only by construction — it cannot write, send or change anything.

  * The verify gate sits BETWEEN the draft and every commit. If it fails, the
    request escalates to a named person. It never degrades into sending.


B2. THE RULE ENGINE — 30 RULES, FIRST MATCH WINS
------------------------------------------------

The rules live in a plain-English config file. They are read top to bottom and
the first one that matches wins, so the ORDER is part of the meaning. The last
rule matches everything, so the agent can never fall off the end of the list.

Here is the whole thing. You do not need to memorise it; you need to know it
exists and is readable, because showing it is more persuasive than describing
it.

  STOP CONDITIONS
   T1  hand_over  A person has taken this matter over, so the agent stops.
   R1  hand_over  A restricted matter goes straight to a named person.
   P1  refuse     Publishing or retiring a policy is a person's decision.
   W1  refuse     Asks about another person's record without standing to.

  ENQUIRIES
   E0  hand_over  Two versions in force — nobody is answered until that is fixed.
   E4  prepare    Too unclear to act on; a person gets a question they can send.
   E1  auto       Routine question, one version in force -> answer, quoting it.
   E2  prepare    Depends on this person's circumstances -> a person confirms.
   E3  hand_over  No policy covers it -> a person answers, not the agent.

  RECORD CHANGES
   A2  refuse     No configured system owns the field this would change.
   A1  prepare    Own record: prepared with a preview, committed on approval.
   A3  prepare    A manager, for a direct report.
   A4  prepare    Someone in HR, for anyone — a second person still approves.

  DOCUMENTS
   D0  hand_over  Message claims an attachment and none arrived.
   D1  hand_over  Restricted type -> files nothing, extracts nothing.
   D2  hand_over  Unrecognised -> a person decides what it is.
   D3  prepare    Incomplete -> names exactly what is missing, chases nobody.
   D4  prepare    Complete -> a person confirms the reading before filing.

  JOINING AND LEAVING
   O1  prepare    Readiness check: reports gaps, closes none of them.
   O2  refuse     Start date too far away to say anything useful yet.
   X1  refuse     An exit is started by a person, never by the agent.
   X2  prepare    Departure checklist, for the case owner to act on.

  SCHEDULING AND STATUS
   I0  hand_over  No calendar connected -> it does not guess availability.
   I4  prepare    Cancelling withdraws a commitment to a candidate.
   I2  prepare    Rescheduling takes back a time already given.
   I3  prepare    No time fits the company's limits -> a person picks what to relax.
   I1  prepare    Scheduling puts time in other people's calendars.
   S1  auto       Telling someone the state of their own request.
   J1  prepare    A scheduled job reports and changes nothing on its own.

  CATCH-ALL
   Z1  hand_over  Nothing matched -> a person decides what this is.


B3. THE GUARANTEE THAT MAKES IT SAFE TO SELL
--------------------------------------------

A company may move any rule to a MORE restrictive mode. It may add a citation
requirement. It can never do the reverse.

This is not a policy or a warning. The software REFUSES TO START. If a
customer edits their config to let the agent answer something the base rules
say needs a person, the loader raises an error and nothing boots.

Which means: no customer setting, and no instruction smuggled into a document
or an email, can unlock a send that needs a human. Say that sentence slowly in
a demo. It is the most valuable thing in the product.


B4. THE VERIFY GATE — 12 CHECKS
-------------------------------

The last thing between a draft and the world. Every check returns pass, fail or
skip WITH A REASON, and the whole list is stored on the decision and drawn in
the UI. A failure escalates; it never becomes a send.

The checks are deliberately mechanical — "do the exact words of the policy it
claims to quote appear in the reply" is a string comparison. A gate you can
reason about is a gate you can trust.

   1  A policy is cited                        (when the rule requires one)
   2  The cited words appear in the reply       verbatim, not paraphrased
   3  One version per policy                    never mixes two versions
   4  The cited version is still in force       re-checked, not assumed
   5  No claim about this person's entitlement  it says what the POLICY says
   6  No legal, medical or financial advice     never, in any mode
   7  A restricted matter was not answered
   8  The reply says something                  not an empty non-answer
   9  No identifier the person did not supply   echo vs leak, see below
  10  Every action has an idempotency key       so a retry cannot act twice
  11  Nothing acted before approval
  12  No two actions share a key

Check 9 is worth understanding because it is subtle. An identifier the person
typed themselves, repeated back so they can confirm it before it goes into
their own record, is an ECHO and is fine. One they did NOT supply came out of a
record and is LEAVING — that is a leak, and it fails.


B5. NOTHING REACHES THE WORLD EXCEPT THROUGH THREE VERBS
--------------------------------------------------------

Every connected system — HR system, calendar, document store, email, service
desk, e-signature — is reached through an adapter that supports exactly three
operations:

  read      no side effects, ever
  prepare   writes a plan and a human-readable preview, and nothing else
  commit    acts exactly once, under an idempotency key

A second commit with the same key returns the first receipt instead of acting
again. So a retry, a double-click and a replayed webhook are all harmless.

Each adapter declares in the config which fields it owns. The agent refuses
anything else. And nothing, on any path, including behind an approval, can
write pay or grant access.


B6. THE APPROVAL QUEUE — THREE GUARDS
-------------------------------------

  1. You cannot approve your own request. This applies to HR too.
  2. You cannot approve something assigned to a role you do not hold —
     unless the company's config says your role deputises for it.
  3. The policy the draft quoted is RE-CHECKED at the moment of approval. If
     the policy changed overnight, approving is blocked rather than sending
     stale wording.

Sending something back requires a reason code from a short fixed list, not free
text. Free text is unreadable in bulk — nobody will ever read a thousand notes,
so the reason a draft was wrong is lost the moment it is written. A code turns
every rejection into a labelled error class, and it tells you WHICH part of the
agent was wrong: retrieval, the facts, the drafting, or the rules themselves.


B7. THE AUDIT TRAIL
-------------------

Append-only and hash-chained per company. Each row's hash covers the row before
it, so editing or deleting history breaks the chain visibly. There are no
UPDATE or DELETE statements against the audit table anywhere in the codebase,
and a test asserts that.

Every decision also records the exact configuration that produced it, as a
hash. Months later you can prove what the system was told to do at the time.

HONEST LIMITATION, and say it before anyone asks: truncating the END of a chain
leaves a valid chain. Detecting that needs an external anchor — a published
head, or an append-only store — which this build does not have yet. The
dashboard states this limitation on screen rather than hiding it.


B8. WHICH AI MODEL IS THIS USING?
---------------------------------

None. Right now, zero. No model is called at any point.

Replies are templates wrapped around policy text quoted verbatim.
Classification is regular expressions and the company's own word lists. This is
a deliberate design choice, not a gap: the whole point is that the answer is
the policy's exact words, so there is nothing for a model to generate.

The interface for a model exists and is one config line. Where a model is
turned on, it is bounded by two rules that cannot be configured away:

  * The model may RAISE how sensitive it thinks something is. It may never
    lower it.
  * The model is NEVER asked what the agent is allowed to do. That is the rule
    engine's job, and it reads facts, not prose.

Templates-and-retrieval must always remain a working mode. That is the floor.


B9. WHAT IS ACTUALLY BUILT (code size)
--------------------------------------

  Tests               4,230 lines across 17 files (416 tests)
  Dashboard           3,394 lines (React + Vite, 10 screens)
  Company packs          63 files across 3 companies

The main modules, so you can answer "where does X live":

  engine.py       the rule engine; the only thing that decides autonomy

  forms.py        reading a form against a company's templates
  tools.py        the adapters, and the prepare/commit machinery
  approvals.py    the queue and its three guards

  scheduler.py    the nightly checks

 PART D — QUESTIONS, TRAPS, AND WHAT IS NOT BUILT
===============================================================================

D1. QUESTIONS YOU WILL GET
--------------------------

"Which AI model is this using?"
  None, right now. Zero. Replies are templates wrapped around policy text
  quoted word for word, and classification is rules and the company's own word
  lists. That is deliberate: the answer IS the policy's exact words, so there is
  nothing to generate. The interface for a model exists and is one config line,
  and where it is on, the model can only ever raise how sensitive something
  looks — never lower it, and never decide what the agent is allowed to do.

"What if the AI gets it wrong?"
  It cannot send an answer it cannot cite to a policy version in force. If it
  cannot, a person gets it. And nothing touches a real system without somebody
  clicking approve.

"Can it handle our company's policies?"
  That is the whole design. Your policies, your rules, your form templates,
  your roles, your working hours, your approval chains — all configuration.
  Onboarding is filling in a config file and getting your own acceptance cases
  to pass.

"Does it connect to our calendar? Google? Outlook?"
  Google Calendar and Gmail are in the box and work through the same adapter
  interface everything else uses — swapping to them is one config file and
  three environment variables, with no change to the kernel, the rules or the
  approval queue. Outlook is the same shape of job: one adapter that answers
  "when is this person busy" and "create this event". What you see in the demo
  is a mock, so nothing leaves this room.

"Could it just book the interview itself and save us the click?"
  It could, and we deliberately did not. Booking puts an hour in four people's
  calendars and sends a stranger an invitation — if that is wrong, somebody
  takes a morning off work for nothing. A company can loosen plenty of things
  in config, but the base rules set a ceiling it cannot raise, and scheduling
  is one of the ones pinned to "a person decides".

"Is our data safe? Is it training on it?"
  No training on customer data, and the setting that would allow it cannot be
  turned on. Identifiers are redacted before anything is stored in the event log
  or the audit trail, using a pattern pack the company configures. Every company
  is isolated at the data layer — there is no query anywhere that can return two
  companies' rows.

"What about GDPR / the EU AI Act?"
  The posture is deliberate: it never computes a statutory entitlement. It
  quotes the company's own policy text or hands over. No leave accrual, no
  notice period, no holiday arithmetic anywhere in the code. That removes most
  of the regulatory surface. It also does no hiring decisions, no ranking and
  no screening, which is the heavily regulated slice.

"Is this production-ready?"
  The logic is built and tested — 416 automated tests. The systems it connects
  to are mocks today. Connecting real ones is the next step, and it is adapter
  work, not kernel work. I would be straight with you: this is pilot-ready, not
  deploy-tomorrow.

Anything you do not know:
  "I would have to check that one." Nobody expects you to know everything, and
  guessing in front of a room is how you lose it.


D2. DO NOT SAY THESE THINGS
---------------------------

Being caught overclaiming loses the room. These are the traps.

  DON'T SAY                       SAY INSTEAD
  "It's 100% accurate"            "It can't send an answer it can't cite. If it
                                   can't, a person gets it."
  "It replaces HR people"         "It handles the routine so people spend time
                                   on what needs judgement."
  "It understands employees"      "It classifies requests and quotes policy. It
                                   doesn't judge anything."
  "It's fully automated"          "Anything that touches a real system waits
                                   for a person."
  "It's AI-powered" (as headline) "It's rules and policy-quoting. AI is
                                   optional and off right now."
  "It's ready to deploy tomorrow" "The logic is built and tested. Connecting
                                   real systems is the next step."
  "It books interviews for you"   "It proposes a time and prepares the
                                   invitation. A person approves before
                                   anything is booked or emailed."
  "It screens candidates"         "It never ranks, screens or assesses anybody.
                                   It finds a time and writes the invitation."


D3. WHAT IS NOT BUILT — KNOW THIS BEFORE YOU ARE ASKED
------------------------------------------------------

  * Every connected system is a MOCK. HR system, calendar, email, document
    store — all simulated. The adapter interface is real and a Google
    Calendar/Gmail connector exists, but nothing in the demo talks to a real
    external service.

  * No authentication in the demo build. Anyone can act as anyone from the
    company directory. That is why the server REFUSES to listen on anything but
    localhost while role switching is on — an unauthenticated role switcher on
    a public port is not a demo, it is an incident. Real sign-in exists and can
    be switched on.

  * Audit truncation is not detectable. Removing rows from the END of a chain
    leaves a valid chain. Needs an external anchor; not built.

  * Offboarding checklists (rules X1, X2) and the nightly scheduled checks
    (J1) work and are tested, but no company has an acceptance case for them,
    so they are not seeded into the demo data. They are reachable from the Work
    items and Configuration screens if anybody asks.

  * Interview scheduling counts the notice period from the start of the working
    day, not the wall clock, because the kernel runs on dates so that a run is
    reproducible. It is a documented approximation, not an oversight.

  * No model has ever been evaluated, because none is called. If a customer
    wants one on, that is new work and new testing.
